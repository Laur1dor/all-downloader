# Памятка оператора бота

## Панель статистики в браузере

- `/dashboard` — новые одноразовая ссылка и пароль, сессия и удалённый доступ на 10 минут с момента запроса. Новый запрос отзывает предыдущий доступ.
- `/dashboard local` — ссылка для домашней сети без запуска внешнего туннеля.
- `/dashboard close` или «Закрыть доступ» — отозвать все ссылки и сессии.

Команда доступна только владельцу в личном чате. Ссылка и отдельный пароль действуют десять
минут с момента запроса и используются один раз. Новый запрос отзывает старые ссылки
и сессии. Пароль вводится на странице и не содержится в URL. После
входа ключ исчезает из адреса, сессия хранится в HttpOnly cookie. В базе остаются
только хэши ключей. Через интернет используется временный HTTPS-туннель
Cloudflare; он закрывается по таймеру. Наличие адреса сайта не даёт доступ к данным.
Локальный адрес задаётся `DASHBOARD_LOCAL_URL` в приватном `.env`. Сервис
`scripts/stats-tunnel.service` запускает туннель по запросу; бот не получает Docker socket.

Панель показывает регистрации, пользователей с любым действием кроме `/start`,
пользователей с конвертациями, результаты, объём отправок, площадки и журнал.
Есть периоды и произвольные даты, поиск пользователя, фильтры площадки, результата,
формата, действия и исхода, а также пагинация. По умолчанию владелец исключён из
аудитории; системные события остаются видимыми. Старые `/stats`, `/analytics`
и выгрузки сохраняются.

Журнал действий хранится 90 дней и не содержит текстов сообщений, адресов
скачиваемых публикаций и значений callback. История конвертаций хранится отдельно;
старые записи могут не содержать площадку и формат. Системные запуски и штатные
остановки начинают фиксироваться с установки панели; аварийная остановка без
корректного завершения не может оставить событие остановки.

Команды оператора доступны только аккаунту `ADMIN_ID`. Для аналитики используйте личный чат с ботом.

## Подтверждение отправки медиа

Исходные документы TikTok проверяются не только декодером: заголовок MP4 должен
содержать конечную длительность фильма. Неизвестная длительность `mvhd` требует
пересборки контейнера даже при наличии faststart и исправных дорожек. Видео,
звук и HDR сохраняются без перекодирования. Документный кэш `original_v5`
обходит ранее отправленные файлы без этой проверки.

У H.264 удаляются недопустимые пустые NAL-пакеты типа 0. Если очищенный поток
содержит HDR, именно он используется для SDR-превью. Для исходного документа
сохранность оставшегося потока проверяется хэшем, а готовый файл полностью
декодируется; повреждение полезных кадров не считается исправленным.

`done` означает полученный ответ Telegram, `failed` — явный отказ или сбой до
отправки. `delivery_unknown` означает потерянное подтверждение: файл ещё может
прийти. Бот не повторяет такую отправку автоматически. Неизвестные исходы видны
отдельно в панели и отчётах, их размер не прибавляется к подтверждённым байтам.
Поздний ответ в пределах окна ожидания завершает исходную операцию как `done`.

Xray проверяет закреплённый маршрут Telegram каждые 30 секунд обменом MTProto
с основным и файловыми адресами Telegram. Используется обфусцированный транспорт
с AES-CTR, как в рабочем Bot API: простой незашифрованный req_pq может
проходить через узел, который блокирует рабочие соединения. Открытый SOCKS-порт или успешный HTTPS
не считаются подтверждением исправности передачи файлов. После трёх неудачных
проверок выбирается резерв из бесплатного пула, прошедший три проверки всех
адресов. Работающий маршрут сохраняется; при отсутствии проверенного резерва
текущий адрес не заменяется случайным. Состояние хранится в приватном
`data/telegram_health.json`, переключения видны в журнале Xray. Перестроение
конфигурации переподключает сетевые соединения; бот не повторяет неоднозначные
отправки и не записывает их как подтверждённые.

В старых записях до исправления от 21.10.2026 таймауты могли попасть в `failed`,
а измерения загрузок — в успешные. По одной этой статистике восстановить факт
поздней доставки невозможно; исторические записи не переписываются догадками.

## Диалоги с пользователями

Пользователь пишет `/contact`, затем отправляет текст, фото или файл. Бот пересылает их в операторскую предложку. Ответьте **на служебную карточку или пересланное сообщение** в этой предложке: бот доставит ответ нужному пользователю. Пользователь завершает диалог командой `/end`; после этого ссылки снова обрабатываются как загрузки.

- `/users` — последние пользователи; `/users username` — поиск по username или ID.
- `/tell ID текст` или `/tell @username текст` — написать пользователю, уже запускавшему бота.
- `/tell ID` ответом на готовое сообщение — переслать это сообщение пользователю.
- `/suggestions` — очередь идей и запросов на новые сервисы.
- `/reply НОМЕР текст` — ответить на конкретное предложение.

Не используйте `/tell` для массовых объявлений: для них есть подтверждаемая рассылка.

## Объявления и канал

`/post текст` публикует новость в канале. Ответьте `/post` на готовое сообщение, чтобы сохранить оформление и вложение. Пользователю подписка на канал не нужна для работы бота.

Рассылка через бот начинается только после подтверждения:

1. Подготовьте сообщение с нужным текстом, фото или файлом в приватной группе **TikTokDownloaderFF — рассылки**. Ответьте на него командой `/broadcast`.
2. Проверьте предпросмотр, число получателей и нажмите **«Отправить всем»**. До нажатия создаётся только черновик. Кнопка **«Отменить»** отменяет черновик.
3. `/broadcasts` показывает последние рассылки и позволяет остановить текущую. Отправка идёт не быстрее одного сообщения в секунду; пользовательские ответы и загрузки имеют приоритет.

Получатели берутся из пользователей, которые запускали бота. Заблокировавшим бота аккаунтам Telegram не позволяет доставлять сообщения; они исключаются из следующих рассылок. Статус «доставка не подтверждена» означает, что Telegram не подтвердил результат сетевого запроса: бот не повторяет такое сообщение автоматически, чтобы избежать дубля.

## Сочетания дефектов исходного MP4 TikTok

Неверная длительность в `mvhd`, заголовок `moov` в конце файла, пустые H.264
NAL type 0 и повреждённая дополнительная аудиодорожка могут встречаться вместе.
Выбор одного ремонта не должен отключать остальные. При необходимом remux
H.264 исходника удаляются также type-0 единицы без изображения. Фильтр
применяется только к первому H.264-видеопотоку (`-bsf:v:0`); для HEVC type 0
может быть допустимым видеопакетом и таким способом не фильтруется.

Используется копирование потоков. SEI и HDR-метаданные сохраняются, хэш
видеопотока сравнивается после исключения только H.264 type 0, а результат
полностью декодируется и проверяется на корректные длительность и faststart.
Исправный исходник с корректным faststart возвращается без изменений.
Повреждение настоящих кадров не маскируется перекодированием или тишиной.

`tests/test_source_document_combinations.py` создаёт настоящие MP4 с
сочетаниями этих дефектов (HLG, PQ и SDR), сверяет хэши потоков и декодированных
кадров, проверяет основной звук, 60 FPS, отмену, отклонение повреждённой картинки
и удаление незавершённых файлов. Тесты входят в автоматический набор CI.
Причина отказа декодера записывается как `TikTok source document validation failed`.

## Дополнительные аудиодорожки TikTok

Полностью скачанный MP4 может содержать исправное видео и основной AAC-звук,
но повреждённую дополнительную аудиодорожку. Перед ремонтом H.264 и
перекодированием бот отдельно проверяет звук и убирает только дополнительные
дорожки, на которых декодер подтвердил ошибку. Исправные дополнительные дорожки
сохраняются; повреждённый основной звук не удаляется и не заменяется тишиной.

Ремонт выполняется через `-c copy`: проверяются параметры, HDR-метаданные и
хэш видеопотока. Готовый MP4 всё равно полностью декодируется перед отправкой.
Если дополнительно повреждены NAL-единицы H.264, следующий этап ремонта
получает файл с уже исправленным набором аудиодорожек. Неудачные промежуточные
файлы удаляются; отмена и лимиты размера сохраняются. Исходный скачанный файл
остаётся отдельно для штатной подготовки кнопки «Файл».

`tests/test_tiktok_auxiliary_audio.py` создаёт настоящие MP4, повреждает пакеты
второй AAC-дорожки и проверяет ремонт, основной звук, 60 FPS/кадры, HDR,
отмену, лимит, неизменность видеопакетов и полный путь выбора превью.
Тесты запускаются автоматически в общем наборе CI без TikTok и GPU.
В журнале `invalid AAC audio packet` отличается от ошибки видеопакетов;
успешное удаление подтверждается сообщением `TikTok auxiliary audio repaired`.

## Очистка Docker и сохранение отката

`docker-maintenance.timer` запускает очистку ежедневно около 03:40 по Москве
(случайная задержка до пяти минут), а также через 15 минут после загрузки.
Сервис использует `/usr/local/lib/adl/docker-maintenance.py`; исходник хранится
в `scripts/docker-maintenance.py`. Ручной просмотр плана: `python3
scripts/docker-maintenance.py`; применение требует явного `--apply`.

Сохраняются образы всех существующих контейнеров, включая остановленные,
обычные теги сервисов (`latest`, `previous` и другие нераспознанные закрепления),
все снимки моложе семи дней и два самых свежих исторических снимка каждого
семейства TikTok, anime и iglogin. Дата снимка берётся из имени тега, если она
новее даты сборки: свежий откат может указывать на старый образ. Удаляются
только распознанные исторические `before`-образы без иных закреплений и
неиспользуемые образы без тегов. Перед удалением ссылки перепроверяются;
принудительное удаление не применяется. Контейнеры, сети, тома и файлы данных
не удаляются и не перезапускаются.

Сборочный кэш очищается с `--all`, `--max-used-space 1gb`,
`--reserved-space 512mb`, `--min-free-space 5gb`. Это цель для удаляемого кэша:
активные записи и слои сохранённых образов остаются, поэтому общий объём
Docker не ограничен одним гигабайтом. Самодеплой применяет тот же лимит кэша.
Очистка и самодеплой используют общий lock; очистка пропускается при сборке
или развёртывании, самодеплой при занятом lock повторится следующим таймером.

Последний отчёт: `data/audit/docker-maintenance-last.json`; журнал:
`journalctl -u docker-maintenance.service`. В отчёте есть свободное место
до/после, удалённые теги, ошибки и проверка сохранности контейнеров. Цель 5 ГБ
не отменяет защиту рабочих образов и откатов. При росте защищённых данных
нужна отдельная проверка; повторное расширение диска не заменяет диагностику.
Отключение расписания: `systemctl disable --now docker-maintenance.timer`.
Таймер самодеплоя остаётся отдельным.

## Регрессионные проверки

`python -m tests.smoke_test` выполняет smoke-проверки и автоматически находит
все unittest-модули `tests/test_*.py` в отдельном процессе, чтобы глобальные
объекты smoke-проверок не влияли на регрессионные тесты. Команда запускается в CI обоих
репозиториев и при самодеплое до перезапуска бота. Новые регрессионные тесты
должны использовать unittest и этот шаблон имени, чтобы не требовать отдельного
включения в список.

Пропуск означает отсутствие необходимого окружения, а не успешную проверку:
GPU требует `NVENC_QUALITY_FIXTURE`, интеграционные тесты PostgreSQL — изолированную
БД (`DASHBOARD_TEST_DSN` или `OPERATOR_DB_INTEGRATION=1`), тест ASR — зависимости
контейнера iglogin. Эти условия видны в skip-декораторах и отчёте unittest.
Аппаратная проверка NVIDIA дополнительно обязательна при настроенном исходнике
на нашем сервере. Живые проверки внешних сервисов и полные сравнения роликов
сохраняются в приватных диагностических отчётах; обычный CI не скачивает их заново.

## NVIDIA для HDR-превью TikTok

`TIKTOK_COMPAT_ENCODER=nvenc` включает NVENC только для совместимого HDR-превью.
Преобразование цвета остаётся прежним: float zscale → Hable → BT.709 на CPU.
Разрешение и FPS не уменьшаются; исходный HDR-документ не перекодируется.
Используется H.264 P7/HQ, VBR CQ22, QP 0–26, multipass, spatial AQ и B-кадры.
Ограничение QP действует на сложные кадры всех типов; одного CQ недостаточно
для предотвращения отдельных просадок качества. Для NVENC через FFmpeg нужно
задавать оба параметра `qmin` и `qmax`. Значение
CQ нельзя напрямую сравнивать с CRF другого кодировщика. На контрольном HLG
1080×1920/60 ролике этот профиль уменьшил время и размер при более высоких
PSNR/SSIM относительно несжатых SDR-кадров. Это измерение конкретного образца,
а не гарантия одинакового выигрыша для любого ролика и GPU.
При недостаточном запасе диска или лимита отправки сохраняется прежний CPU-режим
`veryfast`: профиль NVIDIA проверен относительно обычного CPU-режима `ultrafast`.

Нужны NVIDIA Container Toolkit, совместимые с драйвером хоста библиотеки и
доступ обычного пользователя контейнера к GPU. Локальный `compose.override.yml`
может задавать `runtime: nvidia`, `NVIDIA_VISIBLE_DEVICES: all`,
`NVIDIA_DRIVER_CAPABILITIES: compute,video,utility` и дополнительную группу GPU.
Самодеплой проверяет этот override вместе с новой основной конфигурацией.
В LXC с устройствами `root:render` и правами `0660` задайте в
`/etc/nvidia-container-runtime/config.toml` в секции `[nvidia-container-cli]`
`user = "root:render"`, сохранив `no-cgroups = true` и режим `legacy`.
Без явной учётной записи служебный процесс может запускаться от `nobody`:
тогда после перезапуска Docker контейнер не стартует с ошибкой NVML
`insufficient permissions`, хотя root внутри LXC открывает `/dev/nvidia*`.
Это настройка служебного процесса Toolkit, а пользователь самого бота
остаётся прежним. Открывать GPU-устройства для всех через `chmod 666` не нужно.
Для диагностики сравните `nvidia-container-cli info` с
`nvidia-container-cli --user=0:$(getent group render | cut -d: -f3) info`.
После настройки проверьте новый контейнер с `--runtime=nvidia` и реальным
`h264_nvenc`: проверка уже запущенного процесса не покрывает prestart hook.
На серверах без GPU остаётся CPU-вариант. При ошибке NVENC, изменении геометрии,
неполном файле или потере кадров результат удаляется и обработка повторяется
на CPU; отмена пользователем не запускает повторную обработку.

Для аппаратной регрессионной проверки задайте `NVENC_QUALITY_FIXTURE` — путь
внутри контейнера к приватному HDR-исходнику с движением. На рабочем сервере
используется реальный фрагмент, который выявил просадки сложных B-кадров.
Перед переключением бота самодеплой запускает `tests.test_nvenc_quality`
через его NVIDIA runtime: сравнивает размеры и средние/минимальные PSNR/SSIM
с CPU на одинаковых несжатых SDR-кадрах. Ошибка блокирует обновление.
Исходник не изменяется и не попадает в Git. В CI без GPU и приватного исходника
этот тест пропускается; переносимые проверки повреждений, отмены и CPU fallback
продолжают выполняться. Для ручного запуска используйте тот же unittest-модуль
с настроенным GPU и переменной `NVENC_QUALITY_FIXTURE`.

Кэш превью TikTok использует `video_hdr_metadata_v2`. Старые HDR-превью и
превью с неподтверждённым типом источника готовятся заново, чтобы не повторять
просадки прежнего профиля. Подтверждённые SDR-превью продолжают отправляться
по прежнему file_id. Кэш исходных HDR-документов `tiktok_document_original_v5`
сохраняется.

## Статистика и диагностика

- `/analytics`, `/analytics 7d`, `/analytics 30d` — активные, новые и вернувшиеся пользователи, итоги по сервисам, действия и время отправки файлов.
- `/analytics_export 7d` или `30d` — ограниченный CSV с событиями, загрузками и отправками. Текст сообщений и данные кнопок в него не входят.
- `/stats` — краткая статистика; `/events` — частые действия за сутки.
- `/control` — настройки и состояние маршрутов. Если включён резерв WARP, доступность выхода не подтверждает здоровье собственных VPN-узлов.

Для неисправной ссылки попросите пользователя прислать саму ссылку через `/contact`, чтобы видеть конкретный пример и ответить в той же цепочке.

## Исходная публикация и профиль в отчётах об ошибках

Владелец получает кликабельный профиль, публичную входную/раскрытую ссылку,
действие и параметры для повторной проверки. /errors ID выгружает контекст всех
операций группы. Неверный ввод и подтверждённо удалённая публикация — rejected,
а CDN/тайм-аут/подготовка/отправка остаются учитываемыми сбоями.
Пользователю не направляются диагностические отчёты или просьбы что-либо повторить.
Политика очистки ссылок, миграция старых уведомлений и регрессии:
[Контроль операций и инцидентов](observability.md#ссылки-и-воспроизведение-инцидента).


Для отдельного закрытого журнала создайте группу с владельцем и ботом и отправьте
`/errors_here` от ADMIN_ID. Карточки редактируются автоматически: 🔴 — открыто,
✅ — восстановлено подтверждённым успешным повтором. `/errors` и `/errors ID`
работают в выбранной группе только для владельца; остальные команды панели
сохраняют ограничение личным диалогом. Повтор `/errors_here` не создаёт дублей.
Вернуть уведомления в личный диалог можно той же командой в личке с ботом.


WARP: ответ SOCKS сам по себе не подтверждает VPN. Проверка контейнера обращается
к `cdn-cgi/trace` через его SOCKS и принимает только `warp=on` / `warp=plus`.
Если `warp-svc` завершится, супервизор завершает контейнер, а Docker запускает
его снова. Краткий сетевой сбой сам по себе не запускает цикл рестартов.
Не удаляйте `warp-data`: в нём регистрация и состояние клиента.

Instagram: при явном перенаправлении на вход и подтверждённой блокировке аккаунта
бот прекращает повторять запросы через ту же сессию, но проверяет анонимные
резервы. Ошибка сохраняется в журнале с причиной «Instagram запросил вход».
Обычные сетевые ошибки не считаются блокировкой; анонимные публичные посты
продолжают обрабатываться. Для постов с обязательным входом восстановите доступ
к аккаунту и проверьте `/iglogin` в личном чате владельца.

Ночной бэкап в приватном репозитории обновляет снимок маршрутов и запускает CI.
Шаг `Nightly backup routing regression` выполняется при каждом запуске CI,
включая PR и ручной запуск. Он проверяет TikTok с одним выходом и с дополнительным
выходом из снимка маршрутов. Тест использует синтетический TOML, проверяет
закрытие каждой отдельной сессии и не подключается к внешним сервисам.

### Автоматические коды Instagram

Помощник `iglogin` получает почтовый код по IMAP. Для Gmail настройте
`IG_IMAP_HOST=imap.gmail.com`, `IG_IMAP_USER` и отдельный пароль приложения
в `IG_IMAP_PASSWORD`. Обычный пароль Gmail на сервере отклонён. После включения двухэтапного входа
подключён отдельный пароль приложения; реальная авторизация IMAP проверена 2026-11-10.
Секреты хранятся в закрытом `.env`, в публичный репозиторий не попадают.

`IG_HANDLE` должен совпадать с текущим профилем. Принимаются только свежие
письма для настроенного ящика и профиля от точных доменов Instagram/Meta.
Чтение использует IMAP readonly и BODY.PEEK, не отмечая письма прочитанными.
На `/auth_platform/codeentry/` поддерживается новое поле `email`; на обычной
странице входа оно не считается полем кода. Коды и пароли не выводятся в журнал.

В CI регрессии `tests/test_ig_mail_recovery.py` подхватываются общей unittest-discovery.
Они проверяют MIME/base64, начальный ноль, отбрасывание старых и чужих писем,
поддельный домен, новую форму и чтение без изменения статуса письма.
Реальный вход проверяется отдельно на сервере после настройки почтового доступа.

Сохранённый профиль браузера используется повторно. Проверка сессии уже выполняется
раз в 15 минут; повторные входы имеют backoff и дневной лимит. Искусственная
массовая активность не включается и не гарантирует защиту от блокировки.
Капча, SMS или запрос удостоверения могут потребовать участия владельца.


Проверка браузерного доступа к Gmail 2026-11-10: отдельный сохраняемый профиль
Chromium в контейнере `iglogin` протестирован в headless и обычном режиме через
Xvfb с настроенным серверным маршрутом. Оба входа Google отклонил сообщением
“This browser or app may not be secure”; неверный пароль не заявлен.
Браузерная сессия Gmail в боковой вкладке рабочего компьютера не является
сессией сервера. Автоматическое чтение Gmail через браузер не развёрнуто и
не считается рабочей заменой IMAP. Изменение режима отображения не помогло.

Если устаревший endpoint проверки сессии не даёт определённого ответа, браузер
может подтвердить вход по совокупности признаков: sessionid, корневая страница
Instagram, ссылка с аватаром текущего IG_HANDLE и навигация в Direct, без
видимой формы пароля. Запомненный аккаунт, публичный пост или редирект на
проверку не считаются успешным входом. Неопределённый ответ не запускает
повторный ввод пароля. Это отдельно проверяется регрессиями восстановления.


При входе после почтового кода помощник закрывает штатное предложение
сохранить вход на `/accounts/onetap/`, затем подтверждает сессию и сохраняет
cookie jar. На сервере 2026-11-10 проверен полный путь с чистого профиля:
новый вход → реальное письмо Gmail → автоматическое чтение кода → ввод →
закрытие предложения сохранить вход → сохранение cookie jar. Существующий
рабочий профиль и cookie jar для этой проверки не сбрасывались. Обновление
`iglogin_browser.py` требует пересборки/пересоздания `iglogin`; одного
перезапуска бота недостаточно. Предыдущий образ помощника сохраняется для отката.


### Регулярная проверка браузерной сессии Instagram

`ig-session-check.timer` открывает главную страницу Instagram в сохранённом
профиле дважды в день, в 10:00 и 18:00 по Москве. При подтверждённом входе
помощник обновляет cookie jar, сохраняя сессию для загрузчика. Это техническая
проверка сессии, а не гарантия защиты от блокировки и не имитация человека.
Лайки, подписки, комментарии, сообщения и массовые просмотры не выполняются.

Сервис запускает `iglogin_browser.py --check-only` в существующем `iglogin`.
Проверка не вводит пароль, не решает checkpoint и не записывает результат
ручного/автоматического входа `iglogin_result.txt`. При занятом профиле или
неопределённом ответе она пропускает запуск (код 3), не меняя cookies.
Ожидания освобождения профиля нет, лимит выполнения — 90 секунд.
После простоя пропущенные проверки не догоняются (`Persistent=false`).
Обычный механизм восстановления входа с ограничением попыток сохраняется.

Установка: скопировать `scripts/ig-session-check.service` и `.timer` в
`/etc/systemd/system/`, выполнить `systemctl daemon-reload`, затем
`systemctl enable --now ig-session-check.timer`. Требуется обновлённый образ
`iglogin`, поддерживающий `--check-only`. Состояние проверяется командами
`systemctl list-timers ig-session-check.timer` и
`journalctl -u ig-session-check.service`. Отключение расписания:
`systemctl disable --now ig-session-check.timer`.

Регрессии `tests/test_ig_session_check.py` входят в обычную CI-discovery:
успешная/отрицательная/неопределённая проверка, отсутствие ввода пароля и
checkpoint, обновление cookies только при подтверждённом входе, освобождение
профиля, отсутствие очереди за загрузками и ограниченное расписание.
