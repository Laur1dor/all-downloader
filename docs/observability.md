# Контроль операций и инцидентов

## Что фиксируется

Локальный `data/operational.sqlite3` фиксирует приём действий, решения допуска,
поиск источника, загрузку, подготовку, очередь, отправку, подтверждённые части,
отмену, отказ, неизвестную доставку и предупреждения Python, включая рабочие
потоки загрузчика. Журнал не содержит текстов сообщений, callback payload,
signed CDN URL, токенов, заголовков запросов и текста исключений. Для инцидентов
сохраняются разрешённые публичные ссылки на публикации/треки, username и
параметры операции; произвольный URL не копируется в журнал. Причина —
безопасный класс исключения и место вызова; если обработчик не уточнил причину,
так и написано. Нельзя выдумывать причину по общему тексту отказа.

SQLite — независимый источник оперативных фактов. PostgreSQL получает пачки
по 100 с устойчивыми UUID и `ON CONFLICT DO NOTHING`. Потерянный ответ после
commit не создаёт дубль. Недоступность PostgreSQL не отменяет подтверждённую
доставку и не блокирует запись локального журнала. Старые таблицы статистики
сохраняются; при отказе их записи локальный результат остаётся достоверным,
но автоматически восстанавливается зеркало `operational_events`, а не запись
старой `conversions`. Это ограничение необходимо учитывать при сравнении отчётов.

## Допуск и пределы

- Polling: не больше 64 выполняемых обработчиков; тяжёлых заданий вместе с
  ожидающими — 16 глобально, одно на пользователя, два у владельца.
- Устойчивый бюджет: три тяжёлых операции с пополнением одной за 20 секунд,
  включая владельца. Существующие отдельные лимиты сети/CPU/отправки сохранены.
- Message/chat ID и callback ID подавляют повторную обработку update.
  Каноническая ссылка, пользователь, операция и тайминг подавляют параллельные
  дубли; разные callback-токены одной ссылки тоже объединяются. После успеха
  действует окно 5 секунд для запоздалого второго клика. Разные ещё не раскрытые
  короткие ссылки нельзя признать одним постом без обращения к источнику;
  параллельность пользователя всё равно ограничена.
- Повторяемость ID: скользящее окно последних 10 000 записей, максимум 24 часа;
  старые завершённые ID вытесняются со счётчиком, активные задания не вытесняются.
  Это ограниченный антидубль, а не обещание вечной истории всех Telegram update.
- Рабочий таймаут 40 минут; при прерывании выставляются зарегистрированные
  сигналы отмены. Внутренние сетевые/FFmpeg deadlines остаются короче. Управляющие
  кнопки, включая отмену/качество, не занимают слот тяжёлой задачи.
- Существующая исходящая очередь: 80 запросов (из них максимум 60 массовых),
  ожидание до 120 секунд; одна безопасная повторная попытка после 429 с учётом
  `retry_after`. Потерянное подтверждение отправки медиа автоматически не повторяется.
- Локально до 20 000 событий, 1000 отдельных инцидентов, 5000 квот/заблокированных
  чатов, 256 ожидающих записей из logging. Подробности вытесняются со счётчиками
  фактических отказов/недоставок/переполнений. Неуведомлённые открытые инциденты
  не объявляются исправленными ради освобождения места. Завершённые уведомлённые
  записи могут уступать место новым. WAL ограничивается checkpoint; строки
  не содержат произвольных больших payload. Файл SQLite имеет режим 0600.
- PostgreSQL: хранение 30 суток и целевой предел 100 000 событий; ограниченная
  очистка пачками по 1000. При всплеске предел достигается постепенно, не одним
  тяжёлым удалением. При переполнении локальной очереди зеркало может быть
  неполным, что явно отражает `mirror_overflow`; суммарные счётчики сохраняются.

## Инциденты и уведомления владельца

Каждая операция имеет отдельную область подтверждения. `open → resolved`
происходит только после результата `done` повторения этой же операции/ссылки/
пользователя. Чужой успех, отмена, тишина и отсутствие новых ошибок ничего не
закрывают. Новый отказ после восстановления переводит запись в `reopened`.
Перезапуск помечает незавершённые операции `interrupted`; они не воспроизводятся
автоматически, поскольку Telegram мог принять предыдущий запрос.

Уведомления объединяются по источнику, этапу и классу причины; разные операции
остаются отдельно проверяемыми. Сообщение содержит русское описание, этап,
источник, контекст своей/чужой операции, число доставленных частей, подтверждённый
или неизвестный исход, повторы, время МСК и диагностический ID. Для группы
показывается число открытых и восстановленных операций. Успех одного участника
не объявляет восстановленной всю группу.

Не более одного уведомления/редактирования в минуту, не более шести новых
сообщений за 10 минут; существующее сообщение группы обновляется не чаще раза
в пять минут. Бюджет новых сообщений переживает перезапуск. Накопившиеся группы
и переполнения отражаются в сводке и `/errors`, вместо отдельного сообщения
для каждой ошибки. Если ответ первой отправки алерта потерян, повторная отправка
запрещена; запись остаётся доступна через команду. Начатая перед падением отправка
тоже считается неопределённой. Служебные 429, истёкшие callback/удалённые статусные сообщения и ожидаемые
пользовательские ограничения учитываются, но не объявляются падением сервиса.
Ошибка sendVideo/sendDocument BadRequest остаётся настоящим сбоем доставки.

После Telegram Forbidden для чата выставляется устойчивый запрет отправки,
текущие сигналы отмены включаются, оставшиеся части не отправляются, следующая
загрузка в этом задании не начинается. Новое входящее действие позволяет новую
попытку, но закрывает инцидент блокировки только реальная успешная отправка.
Массовая рассылка также фиксирует частичные/неопределённые/заблокированные результаты.
Потеря PostgreSQL не должна убивать её supervisor при попытке записать восстановление.

## Доступ и восстановление

`/errors` доступен только владельцу в личном чате: счётчики и последние четыре
инцидента. `/errors ID` выгружает безопасный JSON выбранного инцидента. Публичный
репозиторий не содержит журнал, SQLite, резервные копии и рабочие секреты.

Перед выпуском остановить таймер автодеплоя на время подготовки; проверить
активность и сохранить прежний image/исходники. Штатный выпуск обязан пройти
smoke, обе CI и реальную GPU-проверку. После установки проверить health,
живой SQLite/зеркало, polling и восстановить таймер. Новый выпуск позволяет
проверять активные задания непосредственно по `claims.state='running'`.
Не заменять работающий процесс с активными задачами. Скрипт
`scripts/operational-drain.py` атомарно ставит маркер в той же блокировке SQLite,
что и допуск; ждёт максимум 30 секунд, затем откладывает выпуск, если задания
остались. Служебные команды/отмена работают. Маркер удаляется EXIT-trap выпуска
и имеет срок на случай аварии. При первом выпуске со старой версии журнала
ещё нет: эта автоматическая гарантия к старому процессу неприменима, нужны
операторские проверки старой активности. Отказы допуска сопровождаются
уведомлением не чаще раза в минуту на пользователя, максимум 10 за минуту глобально.

При откате вернуть предыдущие исходники/image штатным способом. SQLite сохранить:
его удаление теряет антидубли, запреты чатов и незакрытые инциденты. Для резервной
копии использовать SQLite backup API, а не копировать только основной файл при
активном WAL. При недоступности самого локального диска новые тяжёлые операции
не должны начинаться без допуска; polling может отвечать ошибкой обработки,
а не принимать неучтённую работу. Это не замена внешнему мониторингу процесса/хоста.

## Проверки

Автоматический unittest discovery включает `test_observability.py` и
`test_observability_postgres.py`. Проверяются 100 ссылок/кликов, глобальная
ёмкость, квоты, перезапуск, независимое закрытие/повторное открытие, частичная
доставка и блокировка, конечный 429 retry, секреты, переполнение, объединение
разных операций в один алерт, устойчивый бюджет алертов и потерянное подтверждение.
В CI обоих репозиториев поднимается отдельный PostgreSQL: тест действительно
записывает пачку, теряет её подтверждение, повторяет её без дублей, разрывает
соединение и восстанавливается. Используются только TEMP-таблицы.

Автоматическое исправление кода моделью не подключено. Экспорт JSON лишь
описывает будущие обязательные этапы: изолированный патч, регрессии, CI,
согласованный выпуск и откат; сам экспорт ничего не запускает.

### Проверка отсутствия блокировки SQLite

Очистка пустой очереди тоже открывает write-транзакцию SQLite. Перед ранним
выходом из idle-notify, возвратом повторного update/отказа и любым сетевым
ожиданием транзакция завершается. Регрессии открывают второе настоящее
SQLite-соединение: оно должно получить BEGIN IMMEDIATE, а допуск следующего
задания — пройти после холостого цикла уведомлений. Первая живая проверка
обнаружила этот пропуск; выпуск был откачен при нуле активных заданий,
до повторного выпуска добавлены эти проверки.

Интеграционный тест запускает сам background-worker с настоящим закрытым
PostgreSQL-соединением, принимает задание при отказе БД, затем подключает новую
TEMP-сессию и проверяет перенос недоставки, подтверждённое resolved и свободный
допуск после холостого цикла. Уведомитель в этом тесте открывает второе SQLite-
соединение; отправок в Telegram из теста нет.


## Ссылки и воспроизведение инцидента

По запросу владельца от 2026-11-05 уведомления и /errors содержат явную HTML-ссылку
на Telegram-профиль: username при наличии, иначе tg://user?id=ID. Цифровой ID
не отдаётся автопарсеру как телефон. Preview внешних ссылок отключён.

bot/incident_context.py собирает только разрешённую публичную входную ссылку
и, после раскрытия короткой ссылки, адрес самой публикации. Остаются только
известные домены/форматы постов и необходимые идентификаторы: YouTube v,
Rule34 id, Pornhub viewkey и т.п. Остальные query/fragment, userinfo, неизвестные
хосты, CDN/прямые signed media URLs исключаются. Каждая ссылка ограничена 512
символами, username — 32. Текст сообщения, секреты и callback-токены не сохраняются.

Сохраняются действие (Видео/Файл/Музыка/Фото), проверенный интервал, выбранная
высота качества, метод отправки Telegram и класс нижнего исключения. Владелец
получает инструкцию проверки по этим параметрам. Контекст живёт в SQLite,
зеркалируется в JSONB PostgreSQL и сохраняется при восстановлении после рестарта.
В /errors ID экспортируются все участники ограниченной группы и их ссылки;
одна сводка не создаёт сотню отдельных уведомлений. В тексте сводки показан
последний незакрытый пример группы. Диагностика направляется только владельцу;
дополнительные сообщения с отчётом или просьбой воспроизвести отправителю не создаются.

Ожидаемый failed для неверного текста/адреса, неподдерживаемого сервиса
или подтверждённо отсутствующей публичной страницы 404/410 нормализуется
в rejected и не создаёт инцидент. Неизвестное «unavailable» само по себе не подтверждает удаление:
ошибка CDN/API/соединения, подготовки или отправки остаётся настоящим отказом.
Неподтверждённая отправка сохраняет delivery_unknown независимо от ввода.
Учитывается и раскрытый адрес страницы, чтобы 404 после короткой ссылки не
перепутать с ошибкой CDN. Ошибочный ввод не превращается в инцидент при рестарте.

При миграции старого SQLite добавляется context, существующие уведомления
обновляются с профильными ссылками. Историческую ссылку, которую прежняя версия
не записала, восстановить по хэшу нельзя: отчёт прямо отмечает отсутствие,
не подставляет догадку и не закрывает неподтверждённую доставку.

Проверки tests/test_incident_context.py охватывают сервисы/ссылки, секреты и
HTML, профили, параметры воспроизведения, callback File, owner-only отправку,
отказы ввода/404, настоящие CDN и media API ошибки, старую схему, перезапуск и
экспорт всех участников. Реальный PostgreSQL-тест проверяет сохранение
очищенной ссылки в JSONB после потери подтверждения commit.
